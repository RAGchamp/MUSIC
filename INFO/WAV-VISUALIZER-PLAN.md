# WAV Visualizer: plan

**Status:** built (2026-11-16): `NOTES-TESTER/WAV-VISUALIZER.html`. Decisions in section 11. Built as planned, except:
two boxes also match when they overlap by at least half (not only when their starts are within ±80 ms); the page has
no dark mode (the other pages don't either); the TEST-FILES lookup needs Chrome or Edge. Checks: the same file on both
sides gives 100 % matched; the generated Pehla Nasha file reads back 186/189 note lines; Analyse took ~16 s for two
73 s files on the build PC (expect longer on the owner's PC).

## 1. Goal

A new page, `NOTES-TESTER/WAV-VISUALIZER.html`, that shows **what notes are sounding** in two WAV files of
the same song, side by side, so the differences can be seen at a glance:

- **Left box: Original**, a recording from `REFERENCE-AUDIO-FILES/` (e.g. `SONG-3-pehla-nasha-start.wav`).
- **Right box: Generated**, the WAV the Notes Tester saved from the notes (e.g.
  `NOTES-TESTER/TEST-FILES/SONG-3-pehla-nasha-start-from-notes.wav`).

In each box every detected note is drawn as a **small coloured box** on a time × pitch grid (a "piano roll"):

- left edge = when the note starts, width = how long it lasts;
- row = the note's pitch (C2 at the bottom … C7 at the top), labelled on the left like piano keys;
- colour = the note name (all C's one colour, all D's another, …), with the name written inside when it fits;
- brightness = how strong the note is.

Both boxes share the same time axis, zoom, scroll and playhead, so the same moment is always at the same place in
both. Notes that appear in only one of the two files are outlined in red, so the eye goes straight to them.

The point: the Notes Tester's text report says *which lines* are wrong; the visualizer shows *what the recording
actually plays* around them, which makes working out the right note much faster.

## 2. What the boxes can and can't show (important)

Like the Notes Tester's Compare, this is a **musical** picture, not a waveform. A WAV file doesn't contain notes;
they are estimated from the sound with the same signal processing the tester already uses (STFT, harmonic salience,
spectral-flux onsets, tuning offset).

- The **generated** file is clean (one instrument, exact notes), so its boxes should match the note lines closely.
- The **original** has accompaniment, voice and reverb, so its picture has extra boxes (chords, bass, echoes) and
  can miss quiet melody notes. That's why the controls in section 5 let you narrow it down (strength threshold,
  pitch range, "melody only").
- **Both files go through the same analysis**, with the same settings. A difference between the boxes is then a
  difference in the sound, not in how each was analysed.

## 4. Choosing the two files (step 1)

Two pickers side by side, one per box:

1. **Original recording:** a file picker (`<input type="file" accept=".wav">`).
2. **Generated by the Notes Tester:** a file picker.

Shortcuts, when the page is served over http(s) (GitHub Pages or a local server):

- A **song drop-down** (from `../REFERENCE-AUDIO-FILES/song-library.js`). Choosing a song fetches
  `../REFERENCE-AUDIO-FILES/<audio>` into the left box automatically.
- For the right box, if the Notes Tester already has its save folder (IndexedDB `notes-tester` / `saveDir`, the
  `TEST-FILES` folder handle), the page looks there for `<audio minus .wav>-from-notes*.wav` and lists the matches
  (`-from-notes`, `-from-sheet`, `-band`, `-tuned`). One click loads it. Otherwise the file picker is used.

On `file://`, `fetch()` doesn't work, so only the pickers are shown (as the Notes Tester does).

**Checks** after loading, shown as a yellow warning (not an error):

- The two file names don't share the song stem (`SONG-3-pehla-nasha-start…`): "these may be different songs".
- The lengths differ by more than 0.5 s: "the times may not line up". The Notes Tester renders the generated file
  to the original's length, so normally they match.

When a song is chosen (or recognised from the file name), its **note lines** are loaded too, for the optional
outlines in section 6.

## 5. Finding the notes in each file (step 2: ▶ Analyse)

One **Analyse** button runs on both files, with a progress bar (the owner's PC is slow; expect ~3–10 s per minute
of audio there). The DSP is the Notes Tester's JS port of `SCRIPTS/musicdsp.py`, **copied** into the page (the
project keeps each page self-contained, as with `tone()` and `ksBuffer()`):

1. **Mono, 22 050 Hz** (`toMono`), **tuning** offset (`estimateTuning`), measured on the original and applied to
   both so the rows line up with the recording's tuning.
2. **STFT** 4096 / 8192, hop 256 (≈ 11.6 ms per frame), two frames per complex FFT (`frameMag2`).
3. **Harmonic salience** for every semitone C2–C7 (MIDI 36–96), 6 harmonics, per frame (`makeAnalysis`).
4. **Peaks per frame:** keep notes whose salience is a local maximum across pitch and at least the
   **strength threshold** × that frame's strongest note (default 0.35). At most **N notes per frame** (default 3).
   An octave or a twelfth above a stronger note is dropped unless it is clearly stronger than its harmonic would be
   (stops overtones showing up as notes).
5. **Group into note boxes:** consecutive frames with the same pitch form one box; a new box starts at an onset
   (`detectOnsets`) even if the pitch stays, so repeated notes show as separate boxes. Boxes shorter than 50 ms are
   dropped; gaps under 30 ms are bridged.
6. **Melody only** (a toggle, off by default): instead of steps 4–5, a single lead line per frame from the
   Viterbi tracker of `SCRIPTS/track_melody.py` (octave penalty 0.2, jump cost 0.2), cut into boxes at onsets and
   pitch changes. This gives the cleanest picture for a flute or vocal line over a band.

Each box keeps: start, end, MIDI note, name (`F#4`), strength 0–1, and the onset time it was cut at.
The settings sit in a `CFG` object at the top of the script, like the Notes Tester.

Changing a setting (threshold, notes per frame, melody only, pitch range) re-runs only steps 4–6 on the stored
salience, which is quick; the STFT isn't recomputed.

## 6. The two boxes (step 3)

```
┌──── Original: SONG-3-pehla-nasha-start.wav ────┐ ┌── Generated: …-from-notes.wav ──────────────┐
│ C6 │        ▇▇D5                                │ │ C6 │        ▇▇D5                            │
│ B5 │   ▇▇▇B4      ▇A4                           │ │ B5 │   ▇▇▇B4      ▇A4   ▇G4  ← red: only here│
│ …  │ ▇G4 ▇▇E4  ▇▇▇ ▇                            │ │ …  │ ▇G4 ▇▇E4                                │
│    └──┬────┬────┬────┬──── 12 s  13 s  14 s     │ │    └──┬────┬────┬────┬──── 12 s 13 s 14 s  │
└─────────────────────────────────────────────────┘ └─────────────────────────────────────────────┘
   ▶ play original     ▶ play generated     ▶ play both (left / right ear)        zoom − +   ⟲
```

- **Layout:** two equal columns on a laptop (Bootstrap `col-lg-6`); on a phone (< 768 px) the boxes stack, left
  box on top, with the same time axis.
- **Grid:** one row per semitone; black-key rows slightly darker, a line at every C with its label; time ticks
  every second (every 0.5 s when zoomed in). Only the pitch range that either file uses is shown (shared by both
  boxes, so rows line up).
- **Colours:** one hue per note name (12 hues), lighter for higher octaves and darker for lower ones, chosen to
  be distinguishable on white (and in dark mode), with a legend above the boxes. Sharps use the same hue as the
  note below, a bit more saturated, so `F` and `F#` look related. Strength sets the opacity (weak = pale).
- **Differences:** each box is matched with the other file's boxes (same note, start within ±80 ms, the Notes
  Tester's threshold). Unmatched boxes get a **red outline**; an "Ignore octave" toggle counts `E4` vs `E5` as an
  octave mismatch (orange outline) instead. A summary line counts them: "Original 212 boxes, Generated 190,
  matched 171, only in original 41, only in generated 19". A **Differences only** toggle fades the matched boxes.
- **Note lines overlay** (toggle): the song's written note lines from `song-library.js` drawn as thin dashed
  outlines in both boxes, with their line numbers, so you can see which line a wrong box belongs to.
- **Zoom and scroll:** both boxes scroll and zoom together (mouse wheel + Ctrl, the − / + buttons, or pinch on a
  phone). The default shows ~10 s across. A minimap strip under the boxes shows the whole song and the visible window.
- **Hover / tap a box:** a tooltip with "F#4 · 12.34–12.61 s · strength 0.82 · line 41 (written G4)".
- **Click a box:** plays that slice of *that* file (start − 0.2 s to end + 0.2 s) and plays the note with the
  Notes Tester's single-note voice, so you can hear the recording and the pitch name together.
- **Playback:** ▶ Original, ▶ Generated, ▶ Both (original left ear, generated right ear, via a `StereoPannerNode`).
  A yellow playhead (`--biz-yellow`) moves across both boxes, and the view scrolls to keep it visible. Speed
  50–125 % and Loop the visible window, as on the practice page. Space plays / stops.

Drawing: the grid and boxes are drawn on a `<canvas>` per box (a 70 s song can have 500+ boxes; canvas keeps
scrolling smooth on the slow PC). Hover and click use a simple hit test on the stored box list.

## 8. Testing

- Open the page from disk (pickers only) and through a local server / Pages (drop-down + fetch).
- **Self check:** load the same file in both boxes → 100 % matched, no red outlines.
- **Generated file vs its notes:** the boxes of a `-from-notes.wav` should agree with the note lines for nearly every
  line (the same idea as the Notes Tester's control read-back, ≥ 90 %); if not, the thresholds need tuning.
- **Known differences:** a generated file from a copy of the notes with one line moved by a tone and one by
  0.3 s → those boxes are outlined red.
- All 5 songs load and analyse; time the Analyse step on a 70 s song.
- Headless Chrome via a Node CDP script (as in CLAUDE.md) for the above, plus screenshots at 390 px and 1280 px.

## 10. Out of scope / limits

- The page never edits the song list; Claude Code does that from the copied differences.
- No waveform or spectrogram diff as the main view (a spectrogram background could be added later as a toggle).
- Busy accompaniment will always add boxes to the original that the generated file doesn't have; the red outlines
  are hints to check by ear, not verdicts. "Melody only" and the pitch range are the tools for this.
- Only WAV files (what the recorder and the Notes Tester produce). Other formats may decode in Chrome but aren't tested.
- No AI in the page; it's plain signal processing.
