How the Music Practice App Works

A single web page for practising songs. You pick a song and press ▶ Play: the song's original recording plays, and the note being played lights up in yellow on a piano keyboard, or on a guitar fretboard and tab, and in a row of little note boxes. The recordings are captured with a companion page, recorder.html, and the notes are worked out by Claude Code, which analyses each recording with Python and writes the result into the song list. This document explains the recorder, the note analysis, the practice screen, how the highlight follows the music, and how tapping a key or fret makes a sound. Last updated 2026-11-15.

1The Big Picture: from a Song to a Practice Screen

Four stages

A new song goes through four stages. Two are done by you, one by Claude Code, and one by the page itself every time you press Play.

You · recorder.html1. RecordCapture a few seconds of the song from a browser tab and save it as a WAV file in REFERENCE-AUDIO-FILES.
→

→
Claude Code · files3. Add to the libraryAdd the song to song-library.js and its instrument to SONG-INSTRUMENT.json, commit, push.
→
The page · index.html4. PractisePlay the recording and light up each note on the instrument and in the note boxes, in time.
Things worth knowing up front
  • The whole app is one file, index.html (HTML, CSS and JavaScript). Bootstrap comes from a CDN; there is no build step and no server code.
  • It works in two places: opened straight from disk (file://) and on GitHub Pages at ragchamp.github.io/MUSIC.
  • Play always plays the real recording. The app never re-creates the song with a synthesiser. The only synthesised sound is the single note you hear when you tap a key, a fret or a note box.
  • The notes are data, not code. Each song is a list of text lines such as '10.16 G4@G 0.5': when the note starts in the recording, which note(s), and how long.
  • Five songs today: Inteha Ho Gayi (guitar), Tip Tip Barsa Pani (piano), Pehla Nasha (piano), Chura Liya Hai (guitar) and Anhoni Ko Honi (accordion).

  • Trim an existing audio file: copy the part between a start and an end second into a new file, leaving the original untouched.

Step 1 · Pick a tab: getDisplayMedia()

Clicking 🗂️ Pick a tab to record calls the browser's screen-sharing API, navigator.mediaDevices.getDisplayMedia(). Chrome opens its picker; you choose the tab playing the music and switch on “Also share tab audio”. (Choosing Entire screen with “Also share system audio” records everything the PC plays.)

  • Chrome only offers tab audio together with video, so the page asks for video too and simply ignores it.
  • Echo cancellation, noise suppression and auto gain are switched off, so the music is captured as it is.
  • If no audio track comes back, the page tells you to try again with “Also share tab audio” on.
Step 2 · Listen and record: Web Audio + ScriptProcessor

The shared stream is fed into a Web Audio graph: MediaStreamSource → ScriptProcessor(4096) → silent gain → speakers. The processor hands the page every block of 4096 samples as raw numbers (one array per channel). A ScriptProcessor is used on purpose: it keeps running while the recorder tab is in the background (you are usually looking at the other tab), whereas requestAnimationFrame would pause.

For each block the page works out the loudness in dB (for the level meter) and, while recording, keeps a copy of the block. Three ways to start and stop:

ModeStartsStops
✋ ManualWhen you press ● RecordWhen you press ■ Stop
⏱️ Fixed lengthWhen you press ● RecordAfter the number of seconds you set; the file is cut to exactly that length
🪄 AutoWhen the sound first rises above the threshold (default −45 dB); the block just before is kept, so the first note is not clippedAfter N seconds of silence (default 3 s); trailing silence is dropped, keeping half a second

If you close the shared tab or stop sharing, recording stops by itself.

Step 3 · Build the WAV file

When recording stops, encodeWav() writes a standard RIFF/WAVE file in memory: a 44-byte header (format 1 = PCM, channels, sample rate, 16 bits) followed by the samples, each one clipped to −1…+1 and stored as a 16-bit integer, channels interleaved. The result is a Blob you can play back in the page's audio player before saving.

recorder.html · the WAV layout
"RIFF" <file size> "WAVE"
"fmt " 16  PCM=1  channels  sampleRate  byteRate  blockAlign  16-bit
"data" <bytes>  L R L R L R …   ← each sample: round(x × 32767), x clipped to −1…+1
Step 4 · Save into a folder: File System Access API + IndexedDB
  • 💾 Save writes the file straight into a folder on your PC using showDirectoryPicker() and createWritable(). The first time, you pick C:\Daya\RAGchamp\MUSIC\REFERENCE-AUDIO-FILES.
  • The folder handle is stored in IndexedDB (database music-recorder), so next time the page already knows the folder; Chrome may just ask you to allow access again.
  • The folder name turns red if it isn't REFERENCE-AUDIO-FILES, as a reminder.
  • ⬇ Download instead works in any browser: the file goes to your Downloads folder.
  • After saving, the page shows a ready-made song-library.js entry for the new file.
Trim · Copy part of a file
  • Choose a file, play it in the player, and set Start and End (type the seconds, or press ⏱ Player position to take the player's current time). ▶ Preview selection plays just that part.
  • WAV files are copied byte for byte (parseWav() + cutWav()): the page reads the RIFF chunks, keeps the original fmt chunk and copies only the sample bytes between the two positions. The copy has exactly the same format and quality as the original.
  • Other formats (MP3, M4A…) are decoded with decodeAudioData() and the selected part is saved as a 16-bit WAV.
  • The copy is named name-copy-YYYYMMDD-HHMMSS.wav and saved in the same folder as the original. If the page doesn't yet have permission for that folder, Chrome asks you to pick it once.
Watch out
  • Recording and folder-saving need Chrome or Edge on a laptop. Other browsers show a warning; Download still works.
  • Forgetting to tick “Also share tab audio” gives no sound. The meter stays at the bottom.
  • Starting a new recording when the last one wasn't saved asks before throwing it away.
  • There is also a Python recorder, BLOG\AUDIO-RECORDER.py (WASAPI loopback), which records whatever the PC is playing.

3How Claude Code Finds the Notes in a Recording

The idea

A recording is just a long list of air-pressure numbers (44 100 or 48 000 per second). To light up notes in time, the app needs something very different: “at 10.16 s, a G4 starts and lasts half a beat”. Claude Code bridges the gap by writing and running small Python scripts (numpy and scipy) that look at the sound's frequencies over time, find where notes start, and decide which note is sounding. It then checks and cleans the result, and writes it into the song list.

You ask in plain words, e.g. “Add SONG-4-chura-liya-hai-start.wav as a guitar song with its notes”. Claude Code does the rest and shows you the summary before committing.

What the analysis looks at
Step 1 · Load and look at the whole clip

Read the WAV with scipy, mix the two channels to one, and scale to −1…+1. Note the length and sample rate, and listen to where the interesting part (the intro, the hook) is. If needed, the clip is trimmed first in the recorder.

Step 2 · STFT: turn sound into a picture of frequency over time

A Short-Time Fourier Transform cuts the audio into short overlapping windows (tens of milliseconds each) and measures how strong every frequency is in each window. The result is a grid: time across, frequency up, loudness as the value. A held note shows up as a bright horizontal line at its frequency, plus fainter lines at 2×, 3×, 4× that frequency (its overtones).

Step 3 · Tuning offset: how sharp or flat the recording is

Old film recordings are rarely tuned exactly to A = 440 Hz; tape speed drifts. The strongest peaks are compared with the nearest exact note frequencies, and the average difference is the tuning offset in cents (100 cents = one semitone). All later note decisions are shifted by it, so a slightly flat B4 isn't read as a Bb4.

Step 4 · Harmonic salience: which note is really sounding

Because every note also lights up its overtones, the loudest single frequency is often the wrong note (an octave or a fifth too high). So each of the 12 notes per octave in the range of interest (e.g. C3 to C6) gets a salience score: the energy at its own frequency plus the energy at its 2nd, 3rd, 4th… harmonics, with the higher harmonics counting less. The real note collects energy from all of its harmonics and wins.

For the guitar songs there is a special double-stop score: most Inteha notes are two strings at the same fret (e.g. E5+B4 at fret 12), so pairs of notes a fourth apart are scored together.

Step 5 · Spectral-flux onsets: where each note starts

Spectral flux measures how much the spectrum suddenly gains energy from one window to the next. A plucked string, a struck key or a new syllable makes a sharp jump. Peaks in this curve, above a threshold and not too close together, are the onsets: the start times written into the song list (e.g. 10.16).

Step 6 · Pick, clean and measure the beats
  • At each onset, keep the note with the highest salience in the melody range (e.g. C4–A5 for the vocal tunes, so the bass drone underneath is ignored).
  • Drop weak readings; merge quick repeats of the same note; drop known overtone and bass readings.
  • Find the tempo from the typical gap between onsets, and turn each note's length (gap to the next onset) into beats: 0.5, 1, 1.5, 2…
  • Fix obvious mistakes by hand. For Chura Liya Hai, for example, three readings were corrected (6.22 s G5 → C4, 11.42 s C6 → F4, 21.77 s G5 → C4) and four overtone readings were removed. The Inteha notes were checked against your own tab.
  • Write down what is uncertain: busy sections where the band drowns the melody, octaves that could be either way.

SCRIPTS/musicdsp.py · the core of it, shortened
sr, x = scipy.io.wavfile.read(wav);  x = mono(x) / 32768
f, t, S = scipy.signal.stft(x, sr, nperseg=4096, noverlap=3840)      # frequency × time grid
mag = np.abs(S)

cents = tuning_offset(mag, f)                                        # e.g. -28 for Chura Liya Hai
sal = {m: sum(w**k * energy(mag, f, midi_to_hz(m, cents) * (k+1))   # note + its harmonics
          for k in range(6)) for m in range(lo, hi)}

flux = np.maximum(np.diff(np.log1p(mag), axis=1), 0).sum(axis=0)     # sudden energy gains
onsets = scipy.signal.find_peaks(flux, height=thr, distance=min_gap)[0]

for i in onsets:                                                     # strongest note at each start
    m = max(sal, key=lambda m: sal[m][i])
    ...                                                              # drop weak, merge repeats, beats
Run it yourself

The whole method is saved as scripts in C:\Daya\RAGchamp\MUSIC\SCRIPTS. Section 4. SCRIPTS explains each one.

Limits of the analysis
  • It finds the melody line only, not full chords (Inteha's opening E minor chord was added by hand).
  • When the band gets loud and busy (Pehla Nasha after about 47.8 s, Anhoni Ko Honi after about 27 s), the strongest note may belong to the accompaniment, not the tune.
  • Octaves are not always certain (Bb3 vs Bb4 in Chura Liya Hai).
  • The -notes.txt files are reports; the app reads only song-library.js. The old Inteha notes file comes from an earlier recording and its times don't match the current WAV.

All the signal processing lives here, so the three commands stay short and always measure things the same way. Each function is one step of the method:

There are two window sizes on purpose: long windows tell close notes apart (C3 and C#3 are only 8 Hz apart), and short windows pin down when a note starts.

analyze_notes.py · the first draft of a song's notes
python analyze_notes.py <wav> [options]

What it does, step by step:

  1. Builds an Analysis of the file (tuning, salience, onsets, tempo) and logs each result.
  2. At every onset, averages the salience from 0.03 s after it (skipping the noisy attack) to 0.18 s or the next onset, and keeps the strongest note between --lo and --hi. Notes in --drop are ignored.
  3. With --double-stop, it also looks for the best pair a fourth apart (e.g. E5+B4) and keeps the pair if the lower note is at least 45% as strong.
  4. Drops readings weaker than --weak × the median, and merges a repeat of the same note closer than --merge-gap.
  5. Turns the gap to the next note into beats (rounded to ½, between ½ and 8) and estimates the key.
  6. Prints a report in the style of the -notes.txt files, with a strength column (1.00 = a typical note; below 0.6 = less sure), then the lines to paste into song-library.js. --out also saves the report.

inspect_time.py · what is sounding at these seconds?
python inspect_time.py <wav> <seconds> [<seconds> …] [--lo C3 --hi C6 --span 0.15 --top 6 --tuning N]

For each time it averages the salience over the next --span seconds and prints the --top strongest notes with their frequency (after the tuning offset), score, score relative to the best, and a bar. It lists the onsets within 0.3 s, so you can see whether the time is right. Among the three strongest, it points out any note that is a 2nd–5th harmonic of another. That is the usual reason a reading is an octave or a fifth too high.

check_library.py · check song-library.js against the recordings
python check_library.py [part of a title or file name] [--rank 3] [--all] [--span 0.15]
  • Reads song-library.js with Python (regular expressions, no JavaScript engine): title, audio file and every note line of each song. Comments are skipped; ~, ^ and @string are understood.
  • For each song with audio, it analyses the WAV over the song's own note range (± 5 semitones).
  • For every timed line, it ranks all notes by salience just after that time. The line is OK if any of its notes (for a double stop or chord, either one) is in the top --rank. Otherwise it is printed with ?? and what the recording suggests instead.
  • It ends each song with the measured tuning and a score. --all prints every line, not only the doubtful ones.

Watch out
  • Tempo is the weakest step. Half and double speed fit the same notes. The measured tempo was right for Inteha, Tip Tip and Anhoni but not for Chura Liya Hai or Pehla Nasha. Check the candidates in the log and pass --tempo. Tempo only changes the beat lengths (box widths), not the note times.
  • Melody only: one note, or one double stop, per onset. Chords like Inteha's opening Em are added by hand.
  • Tuning re-measured: these scripts measure Chura Liya Hai at −35 and Anhoni Ko Honi at −44 cents. The earlier reports (in the table in section 3) said −28 and −34. The scripts estimate tuning a little differently from the original one-off analysis.
  • The draft is a starting point: listen against the recording before it goes into the app.

5How AI Helps, and How the LLM Learned to Analyse Audio

The short answer

The AI here is Claude, a large language model (LLM), working through Claude Code, which lets it read and write files and run programs on your PC. Claude does not listen to the music. It can't take a WAV file as input the way it takes text or a picture. Instead it acts like an audio engineer with a lab: it knows the theory, writes the measuring tools (Python scripts), runs them, reads the numbers they print, judges whether they make musical sense, and fixes what doesn't.

So the numbers (frequencies, onset times) come from numpy and scipy. The choices come from the AI: which method to use, which settings, which readings to trust, and how to turn them into a clean song list that the app can use.

A real example from Chura Liya Hai: at 6.22 s the strongest reading was G5. The song is in Bb minor and the notes around it are low, so Claude treated G5 as an overtone (G5 is the 3rd harmonic of C4: 3 × 262 Hz ≈ 785 Hz, an octave and a fifth above it) and corrected it to C4. A plain script can't make that judgement; it needs musical knowledge plus reasoning about this particular clip.

What AI adds
  • Signal-processing know-how: which tools fit (STFT, harmonic salience, spectral flux) and how to set them up.
  • Music knowledge: keys and scales, overtones, tempo and beats, guitar fingering (double stops on the e and B strings, slides, hammer-ons), what a piano accordion is.
  • Judgement: spotting readings that are physically possible but musically wrong.
  • Glue: turns measurements into the exact text format the app reads, then tests the page.
  • Honesty about uncertainty: each -notes.txt report says which parts are less reliable.
  • Speed: a clip is analysed in minutes instead of an evening of transcribing by ear.
What AI does not do
  • It doesn't hear the song. It only sees numbers, so it can be fooled where the numbers are ambiguous (a loud band, octaves).
  • It doesn't guarantee correct notes. The results are a well-reasoned draft for you to check by ear.
  • It doesn't remember between sessions by itself. What it learns about this project is written into .claude/CLAUDE.md and the notes files.
  • It isn't involved when you practise. The app is ordinary code.
How the LLM was trained, and why it can analyse audio at all

Claude was not trained specifically to transcribe music, and it was not trained on these songs. Its ability here comes from general training, in broadly three stages (Anthropic publishes the outline; the exact data and recipes are not public):

Stage 1 · Pre-training: learning from a very large amount of text and code

The model learns to predict the next word (token) across a huge collection of public text and code. To predict well it has to absorb what that text contains: music theory, acoustics (why a string has harmonics), signal-processing textbooks and research papers (including the field of music information retrieval, where onset detection and pitch estimation are standard topics), numpy and scipy documentation, and countless example programs. Here it picks up knowing how to analyse audio.

Stage 2 · Fine-tuning with feedback: learning to be a helpful assistant

The model is then trained with human feedback and with Anthropic's written principles (Constitutional AI) to follow instructions, explain itself, admit uncertainty and avoid harm. This is why it writes a report that says “octaves are not always certain” instead of presenting a guess as fact.

Stage 3 · Training as an agent: learning to use tools

Models like Claude are also trained, largely with reinforcement learning, on tasks where they must write code, run it, read the output and errors, and try again until the job is done. This is what turns textbook knowledge into a working process: Claude Code can run Python on your PC, look at what comes back, and improve the script, the loop shown above.

Compare: AI models trained directly on audio

There is a different kind of AI that is trained on sound. It learns from thousands of recordings paired with the exact notes played (for example the MAESTRO set of piano performances recorded with their MIDI). Examples are Google Magenta's Onsets and Frames and MT3, Spotify's Basic Pitch, and CREPE for pitch. This app doesn't use them today.

8Tapping a Key or Fret: How the Sound Is Made

What you can tap
  • A piano key → that one note, and the key flashes blue.
  • A fret cell (any string, any fret, even ones the song doesn't use; hover shows the note name) → that note on that string.
  • A note box or a tab column → all the notes of that step together (a chord is strummed, 30 ms apart, low to high), and their keys or frets flash.
From tap to sound
pointerdown / click→ hear([midi…])→ ensureCtx(): one AudioContext, master gain 0.7 → compressor → speakers→ tone(m, t, 0.5 s, inst)

Every note is identified by its MIDI number (C4 = 60, A4 = 69). Its frequency is 440 × 2(m − 69)/12, so A4 = 440 Hz and E5 = 659 Hz. The sound is generated live with the Web Audio API; no sound files are used. Each instrument has its own recipe:

🎹 Piano
triangle f+sine 2f × 0.25→gain envelope

A triangle wave at the note's frequency gives a soft, round tone; a quiet sine an octave up adds brightness. The volume jumps up in 10 ms (the hammer strike), then decays towards a lower level and fades out, like a struck string dying away.

🎸 Guitar: Karplus-Strong
noise burst→delay line, averaged each pass→high-pass 70 Hz→body EQ 180 Hz→“air” 2.8 kHz

ksBuffer() simulates a real plucked string: a short burst of random noise, exactly one wave-period long, goes round and round a loop; each time round, neighbouring samples are averaged, so the high frequencies die first, just as on a real string. What's left is a pitched pluck that rings and fades over about 2.6 s. Two EQ bumps imitate the guitar body. The buffers are cached per note.

🪗 Accordion
sawtooth f+sawtooth f × 1.004→low-pass→bellows envelope

Two reeds a tiny bit apart in pitch beat against each other: the wavering musette sound. A low-pass filter takes off the buzz, and the volume swells in over 40 ms (the bellows) instead of starting with a strike.

Good to know
  • Browsers only allow sound after a tap or click, so the AudioContext is created (or resumed) on your first tap.
  • These synthesised notes are only for hearing one note or chord. ▶ Play never uses them: it always plays the original recording.
  • The slide (~) shape is in the code too: the pitch can glide in from the previous note over up to 110 ms.

9Glossary

TermMeaning
WAVAn uncompressed audio file: a short header, then the raw samples.
Sample rateHow many sound measurements per second (44 100 or 48 000 Hz).
dBLoudness on a log scale; 0 dB is full scale, −45 dB is quiet.
STFTShort-Time Fourier Transform: the strength of every frequency in short slices of time.
Harmonics / overtonesThe quieter frequencies at 2×, 3×, 4×… a note's pitch that give an instrument its colour.
SalienceA score for how strongly a note is present, adding up its pitch and its harmonics.
OnsetThe moment a note starts.
Spectral fluxHow much new energy appears from one slice to the next; peaks mark onsets.
CentsOne hundredth of a semitone; used for the tuning offset.
MIDI numberA number per note: C4 = 60, each semitone +1.
Double stopTwo strings played together, e.g. e and B at fret 12 (E5 + B4).
Slide / hammer-on / pull-offWays to reach a note without a new pick: slide the finger along the string; tap a finger down; pull it off.
TabGuitar notation: six lines for the strings, numbers for the frets.
Karplus-StrongA simple, classic way to synthesise a plucked string from noise and a delay loop.
LLMLarge language model: an AI trained on large amounts of text and code to predict and produce text. Claude is one.
Pre-training / fine-tuningThe first broad training on text, then further training with feedback to make the model a careful, helpful assistant.
MusetteThe shimmering accordion sound from reeds tuned slightly apart.
