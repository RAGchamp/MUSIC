How the Piano Notes Player Works

The Piano Notes Player (NOTES-TESTER/Piano-notes.html) takes a notes file, plays it on a recorded piano sound, shows two hands pressing the keys with numbered fingers, and scrolls the score underneath with the current notes in yellow. Part 1 walks through the page step by step, from loading the file to the hands, the sound, the score and playing a range of bars. Part 2 explains how the notes files were made from sheet music: the 5-minute Bollywood song Pehla Nasha from screenshots (partly by eye), and Beethoven's Für Elise from a MuseScore PDF (fully by code). Both songs play in the Piano demo. Last updated 2026-11-16 (Für Elise added).

Part 1 · How the Piano Notes Player works

1The Big Picture

From a text file to moving hands

Everything starts from a plain text file of note lines. The page turns it into a list of lines, decides which hand and finger plays each note, and then drives three things from one clock: the sound, the hands on the keyboard, and the score (as staff notation, or as falling notes on a phone; see section 9).

You1. Choose a filePick a .txt from REFERENCE-AUDIO-FILES, e.g. the 5-minute Pehla Nasha notes.
→
readLines()2. Read the linesEach line becomes {time, notes, beats, label}.
→
splitHands() · place()3. Hands and fingersRight or left hand for every note, and a finger 1–5.
→
pump() · showAt()4. PlaySchedule the piano samples; move the hands; light the keys; highlight and scroll the score.
Things worth knowing up front
  • One self-contained page. HTML, CSS and JavaScript in one file; it only reads files and works opened straight from disk (file://).
  • No recording is played. The sound is built from recorded single piano notes (the FluidR3 SoundFont samples in NOTES-TESTER/SAMPLES/piano.js).
  • The hands are a sensible guess. The notes file does not say which hand or finger plays a note, so the page works it out. It is a reasonable fingering, not the arranger's.
  • No AI runs in the page. Every step is ordinary, repeatable code: the same file always gives the same hands, fingers and sound.
Follow along with Für Elise

2Loading the Notes File

Step 1 · You pick the file

Step 1 of the page has one file box (Notes File, the .txt file from Reference-Audio-Files). A browser page cannot look into a folder by itself, so you choose the file; the page then reads it with file.text(). Nothing is uploaded anywhere.

1Choose the notes Notes File, the .txt file from Reference-Audio-Files
Choose FileSONG-3-PEHLA-NASHA-ORGIG-NOTES-5MIN.txt
📄 996 lines, 5:01. Right hand: 743 lines · left hand: 591 lines.
Step 2 · Each line is read into four parts

The file uses the same line format as song-library.js: time (seconds), notes joined by +, beats (how long until the next line), and an optional label such as bar 5. Quotes, trailing commas and // comment lines are skipped, so the file can also be pasted into the song list unchanged.

SONG-3-PEHLA-NASHA-ORGIG-NOTES-5MIN.txt
//   time  notes                 beats  label
    '  8.98  D5+A3+F3+D3              0.5  bar 5',
    '  9.25  D5                       0.5',
    '  9.52  F5                       0.5',
    '  9.79  D5                       2.5',

readLines() matches each line with one pattern and turns every note name into a key number (MIDI: middle C = 60):

Piano-notes.html · readLines() (shortened)
const m = s.match(/^(-|\d+(?:\.\d+)?)\s+(\S+)(?:\s+(\d+(?:\.\d+)?))?(?:\s+(.*))?$/);
const notes = m[2].split('+').map(tok);      // 'D5' -> {L:'D', acc:'', oct:5, midi:74, name:'D5'}
out.push({t: m[1] === '-' ? null : +m[1], notes, beats: +m[3] || 1, label: m[4] || ''});
// lines written with '-' instead of a time get times from the beats and "tempo: N" in the file
  • First note = main note. In these files the right hand comes first, highest note first, so the first name is the melody.
  • Untimed files work too. If the times are -, the page adds up beats × 60 ÷ tempo, starting at start: (or 0).
  • The lines are sorted by time, and the keyboard is drawn for the song's range (lowest to highest note, rounded out to whole octaves, at least 4 octaves).

3Which Hand Plays Which Note

The problem

A line such as D5+A3+F3+D3 says which keys go down together, but not which hand presses them. A pianist would play the high D5 with the right hand and the D minor chord (D3 F3 A3) with the left. splitHands() makes that choice for every line.

How it chooses: try every split, keep the cheapest

The notes of a line are sorted from high to low. The page tries every way of cutting the list in two (top part = right hand, bottom part = left hand), gives each split a cost, and keeps the lowest:

RuleWhyCost
Distance of each hand's notes from where that hand has been playingHands stay in their area; they don't jump around.1 per semitone
A hand covering more than an octaveOne hand can't reach that far.8 per semitone over
The main (first-written) note given to the left handThe melody is normally in the right hand.4
A right-hand note below D4The right hand rarely goes that low.6 per note
A left-hand note from F4 upThe left hand rarely goes that high.4 per note

After each line, each hand's "centre" moves 30% of the way towards the notes it just played, and the two centres are kept at least 8 semitones apart. The weights were tuned against the hands in the printed score: 975 of the 996 Pehla Nasha lines are split exactly as written (935 before tuning).

4Choosing the Fingers

Five fingers over five white keys

The page measures key positions in white-key units: white key number 0, 1, 2 … across the keyboard, with a black key halfway between its neighbours (e.g. 3.0 between white keys 2.5 and 3.5). A relaxed hand covers five neighbouring white keys, so a hand is described by one number, p: where the thumb (finger 1) rests. Finger f rests at p + f − 1. Finger numbers are the pianist's: 1 = thumb, 2 = index, 3 = middle, 4 = ring, 5 = little finger. The left hand uses the same rule in a mirrored keyboard, so its thumb is on the right.

The rules in place()
SituationWhat the hand does
The notes fit under the hand where it isThe hand stays put; each note goes to the finger over it.
One note, above the handThumb passes under: the new note gets finger 1 and the hand moves up (as in a rising scale).
One note, below the handFinger 3 crosses over: the new note gets finger 3 and the hand moves down.
A chord that fits within five white keysThe hand moves as little as possible so the chord fits, then fingers by position.
A chord wider than the handA stretch: thumb on the lowest note, little finger on the highest, the others shared out in between.
How long a finger stays down

A hand keeps its keys down until that same hand plays again (at most 4 seconds). So a left-hand chord is held while the right hand plays several melody notes over it, the way a pianist holds a chord. This is also how long each note sounds.

5How the Hands Move: Taps and Stretches

What a hand is made of

Each hand is six plain boxes laid over the keyboard: a palm (with R or L) below the keys and five fingers reaching up onto them. The right hand has an orange outline, the left a blue one. The page only ever sets each box's position and length; the browser's CSS transitions animate the change, so the hand slides to a new position (0.16 s) and a finger dips into a key (0.07 s) instead of jumping.

A reach to a black key (left hand, finger 3)

When the key is black, the finger extends much further, to y = 66 px, because black keys sit further from the player and are shorter. A long finger therefore means "this note is a black key" (here B♭2), and the key turns blue for the left hand.

A tap on a white key (right hand, thumb)

Most of the time a finger just dips a little: a white key is pressed near the player, so the fingertip only moves from its resting line (y = 124 px) to y = 112 px, and the key turns yellow.

The finger shapes, in numbers
Finger stateFingertip (from the top of the keys)What you see
Resting (fingers 2–5)124 pxLight colour, just touching the front of the white keys.
Resting thumb140 pxShorter, because a thumb sits lower on a real hand.
Pressing a white key112 pxDarker, a little longer, with its finger number; the key turns yellow (right) or light blue (left).
Pressing a black key66 pxMuch longer: the finger extends up into the black key.
  • Resting fingers follow the pressing ones. Fingers that are not pressing are placed between (or beside) the pressing fingers (fingerXs()), so in a stretch the whole hand spreads out and the palm widens with it.
  • A short lift before the next press. A finger lifts 0.05 s before its note ends, so repeated notes on the same key show as separate taps.
  • A hand that is waiting shows where it will play next, with no finger down.
  • The line above the keyboard spells it out, e.g. Right: F5 (4) · Left: C4 (1) + A3 (3) (note and finger). Finger numbers can be switched off.

6How the Sound Is Made

Step 1 · Load the recorded piano notes

When the page opens it adds SAMPLES/piano.js as a script (this also works from disk). The file holds one short MP3 per key (64 keys, A1–C7, grand piano from the FluidR3 SoundFont, CC BY 3.0). Each is decoded once, its silent lead-in is cut so notes start on time, and its loudness is set to the same peak. A key outside that range falls back to a simple synthesised tone. The status shows 🎹 Piano sound ready (64 recorded notes).

Step 2 · Make each note sound like a piano, softly
  • The melody stands out: the main note of a line plays at full level; the other notes of the line (chord notes, the left hand) at 0.55 ÷ √(number of others).
  • High notes are softer: above D5 each semitone is 3% quieter (down to half), so the top doesn't sound shrill.
  • A pedal-like release: when a note ends it fades over about 0.3 s instead of stopping dead.
piano sample→note volume (main / chord / high-note)→ low-pass 4.2 kHz→treble −5 dB→room echo 20%→compressor→speakers
Step 3 · Schedule the notes a little ahead

Web Audio plays a note at an exact future time. Every 0.25 s, pump() schedules all the lines that start in the next 1.2 s, so even a 5-minute song never has thousands of notes waiting at once. Speed (50–115%) simply divides the gaps: at 50% a 1-second gap becomes 2 seconds, and the pitch is unchanged because each note is still the same sample.

Piano-notes.html · pump() (shortened)
const horizon = from + (ctx.currentTime - t0 + 1.2) * sp;     // song time 1.2 s from now
for(; nextLine < lines.length && lines[nextLine].t < horizon && lines[nextLine].t < until; nextLine++){
  const L = lines[nextLine], when = t0 + (L.t - from) / sp;    // when to play it, on the audio clock
  L.r / L.l notes -> note(midi, when, held / sp, level);       // each hand's notes, held until that hand plays again
}

7The Score and the Yellow Highlight

Building the score from the lines
  1. Bars. A line labelled bar N starts bar N (files without labels are cut into 4-beat bars).
  2. Columns. Each line is one column: its right-hand notes go on the treble staff (black) and its left-hand notes on the bass staff (blue), using the same hand split as the keyboard. Each note is drawn at its height on the staff, with a flat or sharp sign when needed.
  3. Note shapes. A note's length is the time until that hand plays again (in beats): 2 beats or more is an open note, a dot adds half, eighths and sixteenths get flags or are joined by beams within a beat. So a held left-hand chord shows as a half note under four melody eighths.
  4. Names. The note names are written under each staff, highest first.
  5. Rows. Bars are packed into rows that fit the frame's width; each bar shows its number and start time (e.g. 27 · 0:51).
Bar 27: the yellow column is the line being played now (D5 in the right hand, B♭2 in the left).
How the yellow highlight stays in sync

There is one clock: the audio clock. While playing, the song position is

Piano-notes.html
const songTime = () => from + (ctx.currentTime - t0) * sp;   // seconds into the song, at the chosen speed

About 60 times a second (requestAnimationFrame), showAt(songTime()) does everything that depends on the position:

  1. finds the current line with a quick binary search (the last line whose time has passed);
  2. moves both hands and presses or lifts their fingers; lights the pressed keys;
  3. writes the "Right: … · Left: …" line, the time and the progress bar;
  4. moves the yellow highlight to that line's column in the score, and if that column's row is out of view, scrolls the score frame so the row is at the top.

Because the sound, the hands and the score are all worked out from the same clock, they cannot drift apart, even at 50% speed. Clicking a column in the score starts playing from that line.

8Playing a Range of Bars

What you do
Play all notesPlay a range of bars Start bar159End bar162bars 159–162: 4:28 to 4:35

Tick Play a range of bars, type the first and last bar, and press ▶ Play: only those bars play (here bars 159–162 of Pehla Nasha, 4:28 to 4:35), then the page goes back to the start bar so you can repeat it.

How it was built
  1. Two boxes that act as a switch. Ticking one unticks the other (setMode()); the bar boxes only work when "Play a range" is ticked.
  2. Only valid bar numbers. Typing anything but digits is removed straight away. checkRange() then checks that both numbers are bars of this song (1–177 for Pehla Nasha, taken from the score's bars) and that the end is not before the start. If not, a red message explains why and ▶ Play is switched off.
  3. Bars to seconds. The range starts at the start bar's first line and ends where the bar after the end bar begins (or at the last note).
  4. Play only that stretch. play(a, b) sets the stop time until = b: pump() schedules no line at or after it, notes that would ring past it are cut to end there, and the animation stops just after it and returns to the start bar.
  5. Clicks inside the range (a score column or the time bar) play from there to the end of the range; switching back to "Play all notes" starts from the beginning.

9On a Phone: Bigger Keys and Falling Notes

The problem

On a phone (about 390 pixels wide) the laptop layout left little room for music: the top bar took two lines and stayed pinned, the controls wrapped onto 3–4 lines, Für Elise needs 6 octaves of keys (42 white keys at 16 px = 672 px, on a 390 px screen) so a hand was often off the edge, and the score showed less than one bar. So the page now changes its layout on screens up to 576 px wide. On a laptop nothing changes.

What changes on a phone
Part of the pageLaptopPhone
Top barLogo and title, stays at the topOne slim line with a smaller logo; scrolls away
Controls▶ Play, ■ Stop, Speed, Finger numbers, sound status, bar rangeOne row of icons: ▶ ■ ⏱ and the view switch; the bar range, Finger numbers and sound status sit behind a ⚙️ button
KeyboardThe song's whole range fits the widthWider keys that follow the hands (below)
Notes viewStarts on the staff (score)Starts on falling notes (below); the staff is one tap away and shows about 2 bars a row

The phone rules are CSS @media (max-width:576px) rules, plus a check of the keyboard's width when a song is loaded.

A keyboard that follows the hands
  1. Does the whole keyboard fit? If every white key can be at least 18 px wide, it is drawn whole, as on a laptop.
  2. If not, how wide should the keys be? For every line of the song the page measures how many white keys the two hands cover together, and takes the width that is enough 85% of the time. The keys are sized so that span fills the screen (18–34 px a key; Für Elise gets 21 px instead of 16).
  3. Slide to the hands. After each change of hand position, the whole keyboard (keys, hands and falling notes together) slides so the middle of the two hands is in the middle of the screen. A CSS transition makes the slide smooth (0.35 s), and tiny moves are ignored so it doesn't wobble.
The falling-notes view

Instead of reading a staff, you watch the notes come down onto the keys. A switch next to the speed chooses 🎼 Staff or ⬇ Falling notes; phones start with falling notes.

  • Each note is a bar over its own key. It is drawn on a canvas above the keyboard, at the same horizontal position as the key, so it slides with the keyboard.
  • Height means time. The view shows the next 3 seconds. A note t seconds away is t ÷ 3 of the way up, so a bar reaches the yellow line at the keyboard exactly when its key is pressed, and its length is how long it is held.
  • Colours: orange = right hand, blue = left hand, a darker shade over black keys; a bar glows while its key is down, and long bars show the note's letter.
  • Finding your way: a faint line and label at every C (C3, C4 …).
  • It is redrawn about 60 times a second from the same audio clock as the sound and the hands, so it stays in sync at any speed and with bar ranges.
Things worth knowing
  • Try it on your phone: open the Piano demo, press ▶ Try it and pick a song. With Für Elise, watch the blue bars of the left-hand arpeggio (A2 E3 A3) land just before the orange right-hand ones (C4 E4 A4).
  • Very wide hand positions: when the hands are further apart than the screen can show at that key width (for example A1 in the left hand and E6 in the right), the keyboard centres between them and the outer fingers can be just off the edge for that moment.
  • One fix found while testing: on a phone the bar range showed "Infinity", because the list of bars was only built when the score was drawn, and the score starts hidden there. The bars are now worked out when the song loads, whichever view is showing.

11Finding Staves, Bar Lines and Note Heads

Step 1 · Take the pictures out of the PDF

A short Python script (pypdf) saved the 23 embedded images as PNG files, page by page, in order.

Step 2 · Find the staff lines and bar lines
  • Staff lines are pixel rows that are dark across more than half the picture. Five evenly spaced ones make a staff; two staves (treble and bass) make one line of music.
  • Bar lines are pixel columns that are dark all the way from the top treble line to the bottom bass line.
Step 3 · Find the note heads (template matching)

Three tiny samples were cut from the first screenshot: a filled head (quarter and shorter notes), an open head (half note) and a whole note. The staff lines are rubbed out of the picture, then each sample is slid over every position (OpenCV's matchTemplate); wherever the match score is above 0.70 a head is recorded, keeping only the best one in each small area.

Step 4 · Turn a head's height into a note name

Each line or space is one step of the scale. The number of half-gaps between the head's centre and the bottom staff line gives the step, counted from E4 on the treble staff or G2 on the bass staff:

omr2.py (idea)
step = round((bottom_line_y - head_y) / (gap / 2))   # 0 = bottom line, 1 = first space, ...
name = letters_from('E', 4)[step]                    # treble: E4 F4 G4 A4 B4 C5 ... ; bass starts at G2
# the key signature (one flat) then makes every B a B-flat unless marked

The output was a list per bar, e.g. bar 5, treble: D5 D5 F5 D5 · bass: A3 D3 F3 (whole notes). It found most heads, but it also picked up stray marks (slurs, letters, the clefs) and missed some heads that sit on a line or are packed into chords.

12Reading Each Bar

What Claude Code did by looking at the pictures

For every line of music Claude Code looked at an enlarged picture (2× to 4×) next to the list of heads. Where a head was unclear it printed the pixels as text, row by row with the pitch of each row, to see exactly which line or space the head covered. From that it decided:

  • Rhythm: beams, flags, dots, rests, ties and triplets, and so where each note falls in the bar.
  • Flats and naturals: the key's B♭, plus written E♭, A♭ and B♮.
  • Chords and hands: which heads belong together, which voice holds on, and which hand plays them.
  • What to leave out: grace notes (they are drawn smaller), trills and rolled chords.

Each bar was then typed into a data file as (beat position, length, notes) for each hand:

tr.py (the transcription)
B[5]  = ([(0,.5,'D5'),(.5,.5,'D5'),(1,.5,'F5'),(1.5,2.5,'D5')],   # right hand
         [(0,4,'A3+F3+D3')])                                      # left hand: D minor, a whole bar
B[100] = B[40]                                                    # repeats re-use the earlier bar
Examples of the tricky parts
  • Bar 1 checked against the recording: at ♩ = 112 its eighths fall at 0.41, 0.68, 0.95 and 1.22 s; the film recording has A5 A5 C6 C6 at 0.41, 0.70, 0.97 and 1.23 s.
  • Bar 66: the first two low notes are 5 pixels wide instead of 8, so they are grace notes; the bar is C4, then B♭3 held, then a C major chord.
  • Bar 76: what looked like three-note chords high above the staff are two notes each (C6+A5, D6+B♭5), counted from the ledger lines.
  • Repeats: many bars come back (e.g. bars 39–48 return as 99–108 and 159–168); each repeat was compared with the earlier bar before re-using it.

13Checking and Writing the File

Step 1 · Check every bar

A checking script confirmed that all 177 bars are present, every note name is valid, nothing runs past the end of a bar, and both hands fill 4 beats. The only bars that came up short were the ones with rests in them, which is expected.

Step 2 · Beats to seconds

The score's tempo marks set the speed: ♩ = 112 from bar 1, 121 from bar 11, 133 from bar 19 and 146 from bar 23 to the end. Bar 1 starts at 0.41 s (where the recording's first note is), and every later position is beats × 60 ÷ tempo after that. The whole piece comes to 4:59.

Step 3 · One line per moment

All notes struck at the same moment, in either hand, become one line: right hand first (highest first, so the melody is the main note), then the left hand. Beats = time to the next line; the first line of each bar gets the label bar N (and the new tempo where it changes). Held notes are written only where they start. The result: 996 lines.

SONG-3-PEHLA-NASHA-ORGIG-NOTES-5MIN.txt
    ' 21.84  F5+C4+A3+F3                1  bar 11 (quarter = 121)',
    ' 22.33  A4                       0.5',

The same data also became the notes list of the sheet-music page MUSIC-NOTES/SONG-3-pehla-nasha-notes.html (right hand and left hand kept apart there).

Step 4 · Test it

The Notes Tester played all 996 lines and read 981 of them back correctly from its own audio, and the owner listened to the result. Compared with the 73-second film recording only bar 1 lines up, because the film version is a different arrangement.

14What Was Automatic, What Was Not

StepDone byRepeatable?
Pictures out of the PDFPython scriptYes
Staves, bar lines, note heads and their pitchesPython script (template matching)Yes
Rhythm, accidentals, chords, hands, grace notesClaude Code, reading enlarged picturesNo: judgement
Checking the bars; beats to seconds; writing the filePython scriptsYes

So the notes file is not the output of a fully automatic reader. The judgement step is what makes screenshots hard for a plain program. A reliable automatic route needs better input: a MusicXML or MIDI file (every note and length is already there, so a converter is exact), or a PDF exported by MuseScore itself (its notes are music-font characters at exact positions, which a program can read). That second route is exactly what happened with Für Elise: see the next section.

15Für Elise: a PDF Code Can Read by Itself

Why this PDF was different

The owner downloaded Für Elise (Beethoven, WoO 59, public domain) as S-PAD/fur-elise-beethoven-notes.pdf: 3 pages exported by MuseScore 3.6. Inside, nothing is a picture. Every note head, rest, flag, dot, sharp and clef is a character of a music font (Leland, which follows the SMuFL standard) placed at exact coordinates, and the staff lines, stems, bar lines and beams are drawn shapes. So instead of guessing from pixels, a program can simply read the score. No step needed reading by eye.

In the PDFWhat it isWhat the program does with it

Step 1 · Staves, bar lines and bars

Five-line shapes are staves; two make a line of music (18 lines over 3 pages). Upright lines across the treble staff are bar lines; a thick one with dots beside it is a repeat. That gives 106 measures: a short pickup, 103 numbered bars and two 2nd-ending bars (MuseScore leaves those out of its count, so the file labels them "bar 8 (2nd ending)" and "bar 22 (2nd ending)").

Step 2 · Which notes, and how long
  • Pitch: head height + the clef in force at that point + accidentals earlier in the bar; under the 8va line, one octave up.
  • Length: each stem is found at the edge of its head; the beams that actually meet that stem are counted. Dots add half. Bar 77's printed "3"s make triplets, and bars 78–81 (9 sixteenths in a 3/8 bar, with the "3" not printed again) are read as triplets too.
  • When: notes in a column start together; the next column starts when the earliest note still sounding ends. Each hand is timed on its own, and notes beamed across both staves are timed with the hand most of them belong to.
Step 3 · Check every bar

In 3/8 time every bar must hold 1.5 beats in both hands. All of them do, except the opening pickup (two sixteenths) and the 1st-ending bar (one beat), which together make one full bar when the repeat is played. While building the reader, these checks caught four mistakes, each fixed in the program rather than by hand: a whole-bar rest counted at the wrong time, notes from the next line of music picked up, beams of a neighbouring group counted, and the 8va line ending 2 points too late (F♯6 F6 E6 came out an octave high in the chromatic run of bar 80).

Step 4 · Write the file in playing order

The repeats are written out: 106 printed measures become 127 bars played. The score says only Poco moto (no metronome mark), so ♩ = 70 is used. The result is REFERENCE-AUDIO-FILES/SONG-6-FUL-ELISE-BEETHOVEN.txt: 778 lines, 2:42, both hands, in the same format as the Pehla Nasha file:

SONG-6-FUL-ELISE-BEETHOVEN.txt
    '   0.50  E5                         0.25  bar 0',
    '   0.71  D#5                        0.25',
    '   0.93  E5                         0.25  bar 1',
    '   2.21  A4+A2                      0.25  bar 2',     // right hand A4, left hand A2
    '   2.43  E3                         0.25',
    '   9.93  A4+A2                      0.25  bar 8 (1st ending)',
    ' 130.79  Bb6+E4+C4+A3              0.167  bar 80',     // a triplet sixteenth = 1/6 beat
